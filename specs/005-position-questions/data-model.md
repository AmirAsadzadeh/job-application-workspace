# Data Model: Position Preparation and Interview Questions

## Version 6 Positions Document

The existing local document remains the complete source of truth.

| Field | Type | Rules |
| --- | --- | --- |
| `version` | literal `6` | Required |
| `listView` | List View Preference | Preserved unchanged from version 5 |
| `positions` | Position array | Position IDs remain unique; sequence remains canonical Manual order |

Each Position gains:

- `questions: PositionQuestion[]`
- `readingItems: ReadingItem[]`
- `submittedResume: SubmittedResume | null`

All other Position fields retain their version 5 contracts.

## Position Question

| Field | Type | Rules |
| --- | --- | --- |
| `id` | string | Required; unique within the owning position; generated by the server |
| `title` | string | Required; must contain at least one non-whitespace character |
| `category` | Question Category or `null` | Optional |
| `customCategory` | string or `null` | Required and non-whitespace only when category is `other`; otherwise null |
| `answer` | Question Answer Document | Required container; an empty document represents no answer |
| `createdAt` | ISO timestamp | Generated once by the server |
| `updatedAt` | ISO timestamp | Generated by the server and advanced on a saved edit |

Duplicate titles are valid. A question is owned only by the Position whose `questions` array contains it.

## Question Category

Allowed persisted values:

- `javascript`
- `typescript`
- `react`
- `html_css`
- `browser`
- `testing`
- `architecture`
- `behavioral`
- `other`

`null` means Uncategorized. `customCategory` is meaningful only for `other` and is removed when another category or Uncategorized is selected.

## Question Answer Document

The document uses strict Tiptap-compatible JSON and always has this root:

```json
{
  "type": "doc",
  "content": [{ "type": "paragraph" }]
}
```

Allowed block nodes:

- paragraph
- heading with level 1, 2, or 3
- bullet list with list items
- ordered list with list items
- code block

Allowed inline content:

- text
- hard break where valid in prose

Allowed text marks:

- bold
- italic
- HTTP(S) link
- inline code

An empty paragraph-only document is the canonical empty answer and does not produce collapsed answer space.

## Code Block

| Field | Type | Rules |
| --- | --- | --- |
| `type` | literal `codeBlock` | Required |
| `attrs.language` | Code Language | Required |
| `content` | zero or one text node | Raw text preserves characters, spaces, tabs, indentation, and line breaks |

Allowed persisted Code Language values:

- `javascript`
- `typescript`
- `react_jsx`
- `react_tsx`
- `html`
- `css`
- `browser_javascript`
- `json`
- `plain_text`

The persisted value controls the displayed language label. Highlighting grammar aliases do not alter it.

## Create Question Input

| Field | Type | Rules |
| --- | --- | --- |
| `title` | string | Required, non-whitespace |
| `category` | Question Category or `null` | Optional classification |
| `customCategory` | string or `null` | Enforces the category invariant |
| `answer` | Question Answer Document | May be the canonical empty document |

Unknown properties, client-supplied IDs, and client-supplied timestamps are rejected.

## Update Question Input

The update input contains the same four editable fields as Create Question Input. It is a complete replacement of the selected question's editable content; identity and `createdAt` remain unchanged, and the server replaces `updatedAt`.

## Collection Ordering

1. New questions are prepended to the owning array.
2. Display order is descending `createdAt`.
3. Existing array sequence is the stable tie-breaker for equal timestamps.
4. Editing does not move a question because newest-first is based on creation time.
5. Filtering does not modify or reorder persisted data.

## Mutation Rules

### Create

1. Validate the owning position and strict input.
2. Generate a unique question ID and one timestamp for `createdAt` and `updatedAt`.
3. Prepend the question.
4. Advance the owning Position's `updatedAt`.
5. Persist the complete document through the existing queued atomic write.

### Update

1. Validate the owning position, question identity, and strict input.
2. Replace editable fields; preserve question ID and `createdAt`.
3. Advance question and Position `updatedAt` values.
4. Preserve collection sequence and atomically persist the document.

### Delete

1. Validate the owning position and question identity.
2. Remove only that question.
3. Advance the Position's `updatedAt`.
4. Atomically persist the document.

The UI confirmation occurs before requesting deletion. Any failed write leaves prior persisted bytes unchanged.

## Reading Item

| Field | Type | Rules |
| --- | --- | --- |
| `id` | string | Required; unique within the owning position; generated by the server |
| `title` | string | Required; must contain at least one non-whitespace character |
| `url` | HTTP(S) URL or `null` | Optional |
| `notes` | string | Optional plain text; empty string represents no notes |
| `isRead` | boolean | `false` for a newly created item unless explicitly submitted as Read |
| `createdAt` | ISO timestamp | Generated once by the server |
| `updatedAt` | ISO timestamp | Generated by the server and advanced for content or status changes |

Duplicate titles are valid. A reading item is owned only by the Position whose `readingItems` array contains it.

## Reading Mutation Inputs

Create and update inputs contain exactly:

- `title`
- `url`
- `notes`
- `isRead`

Unknown properties, client-supplied IDs, and client-supplied timestamps are rejected. Update replaces all editable fields, allowing the direct compact-row checkbox to use the same contract as the expanded editor.

## Reading Ordering and Transitions

1. New items are prepended and displayed by descending `createdAt`.
2. Existing array sequence is the stable tie-breaker for equal timestamps.
3. Editing notes or changing Read status does not move an item.
4. Read status may change directly between `false` and `true` without another workflow state.
5. No manual order value is persisted.

## Submitted Resume

| Field | Type | Rules |
| --- | --- | --- |
| `originalFileName` | string | Required display name; contains no path semantics |
| `fileType` | `pdf` or `docx` | Derived from staged-file content |
| `mediaType` | supported MIME string | Derived from staged-file content and consistent with `fileType` |
| `relativePath` | string | Required opaque managed path beneath the owning position's resume directory |
| `uploadedAt` | ISO timestamp | Generated when import or replacement succeeds |

`null` means no submitted resume. There is no resume history collection, version label, source absolute path, or embedded binary payload.

Supported type mapping:

| `fileType` | `mediaType` |
| --- | --- |
| `pdf` | `application/pdf` |
| `docx` | `application/vnd.openxmlformats-officedocument.wordprocessingml.document` |

The managed filename is generated independently of `originalFileName`, so duplicate names across positions cannot collide.

## Readiness Mutation Rules

### Create Reading

1. Validate the owning position and strict input.
2. Generate a unique reading ID and authoritative timestamps.
3. Prepend the reading item, advance Position `updatedAt`, and atomically persist JSON.

### Update Reading or Read Status

1. Validate the owning position, reading identity, and complete editable input.
2. Preserve ID and `createdAt`, advance reading and Position `updatedAt`, preserve order, and atomically persist JSON.

### Delete Reading

1. Validate the owning position and reading identity.
2. Remove only that item, advance Position `updatedAt`, and atomically persist JSON after UI confirmation.

### Import or Replace Resume

1. Stream request bytes to a unique staged file outside the visible managed name.
2. Detect and validate PDF or DOCX content and normalize the original filename as display-only metadata.
3. Enter the repository write queue, promote the staged file to a new opaque final path, and atomically persist new metadata.
4. On replacement, retire the previous managed file only after the new file/metadata pair is durable.
5. If any reported step fails, compensate staged changes so the prior visible file/metadata pair remains unchanged.

### Remove Resume

1. Confirm removal in the UI.
2. Enter the repository queue and move the current file to a reversible tombstone path.
3. Atomically persist `submittedResume: null`, then remove the tombstone.
4. If any reported step fails, restore the previous metadata/file pair.

### Open Resume

1. Read the owning Position and current resume metadata.
2. Resolve the relative path beneath the configured resume root and verify it is a regular file.
3. Stream the file with its stored detected media type and safely encoded original filename.
4. If the file was removed externally, return an unavailable result without changing Position data.

## Migration to Version 6

For each valid version 5 Position, add:

```json
"questions": [],
"readingItems": [],
"submittedResume": null
```

Versions 1 through 4 continue through their previously approved description, publication-link, list-view, status, and application-channel migrations before receiving empty preparation collections and no submitted resume.

## Migration Invariants

- Position count, IDs, and sequence do not change.
- List-view mode, sort column, and direction do not change.
- Company, role, assignment, manager, salary, description, timestamps, links, application statuses, and application dates do not change.
- Every migrated Position has empty question and reading collections plus a null submitted resume.
- No migration invents preparation content or associates preparation data with another position.
